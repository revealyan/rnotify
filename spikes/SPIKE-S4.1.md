# SPIKE-S4.1 — свой рендер: WPF vs WinUI 3 (матрица «карточка+столы»)

- Дата: 13.09.2026 (раунды 0–2 + глазная часть; вердикт — «Итог»)
- Машина: Windows 11 Pro 26200 (25H2), один монитор 2880x1800 физ., 150%
- Ветка: `s4.1-render-spike`
- Решения план-гейта: без Islands (доки WASDK: «tested for C++ only»);
  ядро матрицы «карточка+столы» (С1–С8); один монитор; тайбрейкер —
  визуальный паритет с нативным тостом.

## Гипотезы (до эксперимента)

- **Г1**: нативный баннер живёт в правом-нижнем углу рабочей области, зона
  ~700x340 физ.пикс @~90 px от низа; раунд 0 уточняет позицию/размер.
- **Г2 (WPF)**: механика матрицы работает (прецедент старого rnotif §9);
  визуал — имитация акрила, не системный материал.
- **Г3 (WinUI 3)**: `AppWindow`+`OverlappedPresenter` даёт показ без
  активации и топмост; `DesktopAcrylicBackdrop` живёт на безрамочном окне;
  пер-мониторный 150% чёткий из коробки.
- **Г4 (WinUI 3)**: столы — пересоздание окна по `EVENT_SYSTEM_DESKTOP_SWITCH`
  (паттерн старого rnotif) срабатывает и для AppWindow.
- **Г5**: клик по карточке → `SetForegroundWindow` отправителю (ALT-трюк) —
  стеконезависимо (уровень HWND).

### Разбор «невидимости» WinUI (методологическая цепочка, 13.09)

1. Симптом: окно есть (visible=True, rect верный), пикселей в зоне ноль.
2. Ложный след №1: «MoveAndResize убивает контент» — опровергнуто PrintWindow
   (контент жив при любом порядке вызовов).
3. Ложный след №2: «XAML делит координаты SetWindowPos на scale» — артефакт
   **DPI-виртуализации проб**: скрипты без SetProcessDpiAwareness получают
   виртуализированные GetWindowRect (÷scale); «компенсация ×scale» выбросила
   окно за экран (DWM-bounds 3456,2286 при экране 2880×1800). Урок в §10a:
   ВСЕ пробы окон — только из DPI-aware процессов.
4. Истина: WindowFromPoint(центр зоны) = HWND фуллскрин-игры владельца;
   exstyle без WS_EX_TOPMOST → карточка ПОД игрой. WPF-карточка (Topmost)
   на той же машине поверх той же игры видна.
5. Итог: позиционирование AppWindow.MoveAndResize(физ. RectInt32) работает
   корректно и контент не убивает; единственный реальный блокер WinUI —
   z-order (факт 2.3).

## Итог

Матрица: WPF С1–С8 все ✅ (С5 — единственный проигрыш, тайбрейкер). WinUI:
С3 ❌ (topmost недостижим на WASDK 2.4 — 4 пути), С7 ⚠️ (✕ мёртв, белая
рамка кнопки), С5 ✅ (тайбрейкер за WinUI).

Конфликт тайбрейкера с блокером: С5 (визуальный паритет — правило решения
по план-гейту) за WinUI, но С3 — функциональный блокер для диспетчера
уведомлений (карточка обязана быть поверх развёрнутых/фуллскрин окон —
нативные баннеры над borderless-играми показываются, WinUI-карточка под
ними прячется).

**Вердикт владельца (13.09, выбор из {WPF, WinUI 3}): «WPF».** Логика:
функциональный блокер С3 перевешивает материальный тайбрейкер С5 —
имитацию материала в WPF можно итеративно подгонять (S4.2), topmost в
WinUI 3 на WASDK 2.4 не достигается вообще. WinUI переоткрыть, если
найдётся путь topmost. Стек зафиксирован — конституция п.5 закрыта.

## Факты для канона §10d (выжимка)

1. Нативный баннер (эта машина, 150%): 372×110 DIP, поля ~12 DIP от краёв
   WorkArea; баннер виден в t500.
2. WPF: вся механика оверлея работает из коробки (Topmost над borderless-
   фуллскрин, не-активация, столы пересозданием, ALT-трюк); материал —
   только имитация (полупрозрачный фон, «цвет другой немножко»).
3. WinUI 3 / WASDK 2.4 (net10.0, 26200): AppWindow.MoveAndResize(физ.
   RectInt32) позиционирует корректно; unpackaged self-contained жив (бут
   ~3–5 с); НО: WS_EX_TOPMOST не устанавливается (ctor-презентер,
   пост-шоу, SetWindowPos, SetWindowLong — все откатываются XAML-слоем);
   дефолтный Button несёт светлый хром; ✕-клик не сработал.
4. Метод-грабли: пробы окон БЕЗ SetProcessDpiAwareness дают
   виртуализированные координаты (÷scale) → ложные выводы о «пересчёте
   координат» и «компенсациях»; windowFromPoint/PrintWindow — рабочие
   зонды невидимых окон; BMP-дифы зоны валидны только на видимой части
   стола (под локскрином/за фуллскрином — нули без диагноза).
